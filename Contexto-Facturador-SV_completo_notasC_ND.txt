FACTURADOR SV — Contexto del proyecto
=====================================

Documento vivo: resume lo construido, las decisiones tomadas y los aprendizajes.
Última actualización: cierre de Módulos 0-5 + migración Livewire + soporte
FE 01/NC 05/ND 06 con validación schema real (2026-10-16).

------------------------------------------------------------
1. QUÉ ES EL PROYECTO
------------------------------------------------------------
SaaS multi-tenant de facturación electrónica para El Salvador, dirigido a
pequeños emprendedores que se están formalizando ante el Ministerio de
Hacienda (MH).

- Uno o varios negocios se conectan de manera simultánea, cada uno con su
  propia base de datos.
- La integración con el MH no se toca directamente: todo pasa por la
  interfaz App\Contracts\ProveedorDte con dos implementaciones
  (ProveedorDteSimulado para desarrollo, ProveedorDteMH para producción,
  ya construido pero inactivo hasta tener credenciales).
- Aún no hay acceso al ambiente de pruebas del MH: la emisión funciona con
  el proveedor simulado, pero el JSON se valida contra los JSON Schema
  oficiales v4 del MH antes de "firmar".

MÓDULO 2: Catálogos
- Tablas: receptores y productos (+ seeders demo idempotentes con

  excluido). Precio guardado SIN IVA (precio base); se calcula al emitir.

MÓDULO 3: Emisión de DTE
- Tablas: documentos y documento_detalles (snapshot del receptor y de cada
  ítem: sobreviven a cambios/borrados del catálogo).
- Estados (convención 8): borrador -> firmado -> transmitido ->
  validado / rechazado / contingencia. Columna reintentos para contingencia.
- numero_control y codigo_generacion (UUID v4 EN MAYÚSCULAS) se asignan AL
  EMITIR, no al crear el borrador. Borrador con numero_control = en cola.
- Flujo: EmisorDocumentos::emitir() -> job FirmarTransmitirDocumento (cola
  redis "dte") -> validación local contra JSON Schema oficial v4 ->
  generación JSON (GeneradorJsonDte, estructura oficial v4) -> copia en disco
  -> firma (proveedor) -> copia firma en disco -> transmisión (proveedor) ->
  estado final. En validado se guarda la copia para el receptor
  (identificacion + firmaElectronica + selloRecibido, manual 6.5).
- Contingencia: FallaTransmisionException -> estado contingencia + job
  ReintentarTransmision con backoff exponencial (tope 240 min, ~24 h).
- Tenancy en la cola: el job recibe tenantId y hace
  tenancy()->initialize() en el handle y tenancy()->end() en finally.
- IVA del resumen va en tributos con código "20" (CAT-015). No existe
  campo totalIva ni ivaItem en el schema v4.
- AlmacenDte: dtes/AAAA/MM/{codigo_generacion}.json | .jws | .receptor.json
  (retención 10 años, convención 5).

MÓDULO 7: Soporte FE (01) + ValidadorDte real contra schemas oficiales
- La FE usa schema V2 (fe-f-v2.json, version=2), NO v4: receptor con
  tipoDocumento/numDocumento, exige ivaItem y totalIva, PROHÍBE ivaPerci,
  codEstable/codPuntoVenta distintos, resumen sin pagos/subTotal/saldoFavor.
  IMPORTANTE: la única familia v2 es la FE (01); NC/ND/NR/CCF son v4.
- Validación local REAL: app\Services\Dte\ValidadorDte con OPIS/JSON-SCHEMA
  (los schemas del MH son draft-07; justinrainbow solo entiende draft-04 y
  NO SIRVE). El job valida con json_decode($json) SIN assoc (opis exige
  stdClass: un arreglo PHP asociativo se interpreta como JSON-array y falla
  "Array value found, but an object is required").
  Errores extraídos con Opis\JsonSchema\Errors\ErrorFormatter::format().
- Si la validación falla: estado rechazado + respuesta_mh.validacion_local
  con la ruta exacta del campo (formato /cuerpoDocumento/0/...).
- BUG CORREGIDO (costó un rechazo real): receptor_snapshot NO estaba en el
  $fillable de Documento: la asignación masiva lo descartaba y el generador
  armaba el receptor con todo null. Ahora está en fillable + cast array, y
  el generador tiene respaldo con el receptor vivo (datosReceptor()).
- Correlativo numero_control: MAX(secuencia)+1 sobre los últimos 15 chars
  (count()+1 falla con huecos por borradores/rechazados eliminados).

MÓDULO 8: Notas de crédito (05) y débito (06)
- Solo sobre CCF (03) Validado (el receptor de la FE de consumidor final
  no cumple el receptor v4 de notas). documento_padre_id (índice, sin FK).
- EmisorDocumentos::crearBorradorNota(padre, tipo, items) reutiliza el
  pipeline (borrador -> cola -> validación -> firma -> transmisión).
- Diferencias schema NC/ND vs CCF (todas en GeneradorJsonDte):
  identificacion exige "fusion"; emisor PROHÍBE codEstable/codPuntoVenta;
  receptor con tipoDocumento/numDocumento (no "nit") + direccion completa
  requerida; cuerpo exige numeroDocumento (n° control del padre) por línea,
  totalIva/ivaPerci/ivaRete por línea y PROHÍBE psv; resumen sin descu* /
  subTotal / saldoFavor / pagos, con totalIva y codigoRetencionMH; la ND
  además exige numPagoElectronico. NO enviar otrosDocumentos.
- UI: botones "Crear nota de crédito/débito" en el detalle del CCF validado;
  pantalla CrearNota precarga las líneas del padre; cantidades ajustables,
  nunca mayores que las del documento afectado.

3. DOCUMENTACIÓN OFICIAL DEL MH OBTENIDA (2026-10-12)
------------------------------------------------------------
Archivos: Catálogos - Facturación Electrónica.xlsx/pdf (V 1.1),
Manual Técnico v2.0, Manual Funcional V 2.0, y JSON Schema v4:
fe-ccf-v4, fe-nc-v4, fe-nd-v4, fe-nr-v4, contingencia-schema-v4
(los 5 schemas viven en resources/mh-schemas/).

Aprendizajes clave del Manual Técnico v2.0:
- Autenticación: POST {base}/seguridad/auth (form-urlencoded: user, pwd)
  -> body.token ya incluye "Bearer ". Vigencia: 48 h pruebas / 24 h
  producción -> se cachea en Redis (margen 2 h).
- Recepción uno a uno: POST {base}/fesv/recepciondte. Body: ambiente,
  idEnvio (correlativo a discreción), version, tipoDte, documento (JWS),
  codigoGeneracion. Respuesta: estado (PROCESADO/RECHAZADO), selloRecibido,
  fhProcesamiento, clasificaMsg, codigoMsg, descripcionMsg, observaciones[].
  Códigos de error 100-116 (107/108 = token inválido -> re-autenticar).
- Consulta DTE: POST {base}/fesv/recepcion/consultadte (nitEmisor, tipoDte,
  codigoGeneracion).
- Eventos: /fesv/contingencia y /fesv/anulardte (se transmiten ANTES que
  los documentos afectados). Lotes: /fesv/recepcionlote (máx. 100 DTE).
- URLs exactas SIN barra final.
- Firma: el MH prescribe un servicio LOCAL (svfe-api-firmador, Docker) en
  POST {url}/firmardocumento/ con nit, active, passwordPri, dteJson ->
  devuelve el JWS. ProveedorDteMH ya implementa esto.
- Archivo para el receptor: identificacion + firmaElectronica +
  selloRecibido (estructura exacta, regla 6.5).
- QR público: https://admin.factura.gob.sv/consultaPublica?ambiente=XX&
  codGen={UUID}&fechaEmi={YYYY-MM-DD}.

Aprendizajes clave de los schemas v4 + catálogos:
- identificacion.version = 4 (const). tipoContingencia y motivoContin son
  OBLIGATORIAS (anulables). Claves documentoRelacionado, otrosDocumentos,
  ventaTercero y apendice deben EXISTIR (anulables).
- numeroControl: DTE-{tipo}-{M|B|S|P}{codEstable 3}P{codPuntoVenta 3}-
  {secuencia 15} (31 chars, regex oficial). Letra por CAT-009:
  01 Sucursal=S, 02 Casa Matriz=M, 04 Bodega=B, 07 Patio=P.
- codigoGeneracion: UUID v4 en MAYÚSCULAS ([A-F0-9]).
- uniMedida: ENTERO 1-99 (CAT-014: 59=Unidad, 99=Otra). tipoItem:
  1=Bienes, 2=Servicios (CAT-011).
- Tipo de documento CAT-002 (OJO, corrige códigos viejos):
  01 Factura, 03 CCF, 04 Nota de remisión, 05 Nota de crédito,
  06 Nota de débito, 07 Comprobante de retención, 08 Comprobante de
  liquidación, 09 Doc. contable de liquidación, 11 Factura de exportación,
  14 Factura de sujeto excluido, 15 Comprobante de donación.
- Tributo IVA = código "20". Retenciones: 22 (1%), C4 (13%), C9.
- Direcciones (emisor Y receptor) requieren distrito (CAT-008).
  Departamentos CAT-012 (06=San Salvador), municipios CAT-013
  (23=San Salvador Centro).
- Emisor lleva codEstable (4 chars), codPuntoVenta y descActividad.
- La FE (01) es la ÚNICA en schema v2 (fe-f-v2.json, obtenido del paquete
  oficial del MH): version=2, receptor tipoDocumento/numDocumento (sin
  "nit"), exige ivaItem y totalIva, PROHÍBE ivaPerci; resumen sin pagos/
  subTotal/saldoFavor; si direccion va, sus campos son NO anulables.
- Notas (05/06): identificacion exige "fusion"; emisor SIN codEstable/
  codPuntoVenta; receptor tipoDocumento/numDocumento + direccion completa
  requerida; cuerpo con numeroDocumento del padre + totalIva por línea, sin
  psv; resumen propio (ver Módulo 8).

5. CONVENCIONES DEL PROYECTO (reglas de arquitectura + aprendizadas)
------------------------------------------------------------
1. Todo modelo declara protected $table explícitamente (pluralizador
   inglés vs. plurales españoles: costó horas de depuración).
2. Migraciones de tenant en database/migrations/tenant/; corren solas al
   crear el tenant.
3. Columnas monetarias: decimal(12,2), jamás float.
4. Índices en estado/activo y campos de búsqueda en toda tabla de tenant.
5. DTE nunca solo en BD: también en disco (retención 10 años).
6. Receptor guardado como snapshot dentro del documento (columna
   receptor_snapshot JSON + columnas receptor_* mínimas).
7. numero_control y codigo_generacion (UUID v4 MAYÚSCULAS) se asignan al
   emitir, no al crear el borrador.
8. Estados: borrador -> firmado -> transmitido -> validado/rechazado/
   contingencia.
9. Certificado .p12 en disco por tenant, nunca en BD; .p12 fuera de git.
10. Comentarios de código en español; código entregado archivo por archivo
    con pasos de verificación (artisan/tinker).
11. Seeders idempotentes (updateOrCreate con clave natural).
12. Redis solo para colas y cache; nunca como almacenamiento de datos.
13. Jobs que tocan datos de tenant reciben tenantId y hacen
    tenancy()->initialize()/end() explícito en handle/finally.
14. La emisión SIEMPRE pasa por ValidadorDte (schema oficial v4) antes de
    firmar: un rechazo local es más barato que uno del MH.
15. NUNCA base64_encode() la salida de chillerlan QRCode::render():
    devuelve ya un data URI completo (outputBase64=true por defecto en v5).
16. En tinker de Laravel 11/12 NO hay aliases cortos de facades: usar la
    clase completa (Illuminate\Support\Facades\Redis::...).
17. Modelos que viven en la BD central asignan la conexión en el
    constructor: $this->connection =
    config('tenancy.database.central_connection', 'mysql'). NUNCA depender
    de la conexión default (el tenancy la cambia a 'tenant').
18. En PowerShell los escapes tipo bash (\$s, comillas dobles anidadas) NO
    funcionan: se comen las comillas o llegan literales a PHP (parse error).
    Para pruebas puntuales preferir SQL directo (mysql -e "UPDATE ...") o
    escribir el --execute con comillas simples externas y código PHP sin
    variables.
19. queue:work CACHÉA EL CÓDIGO: cualquier cambio en jobs/servicios de cola
    exige reiniciar el worker (Ctrl+C y de nuevo) o el job corre con código
    viejo. En dev alternativo: queue:listen (recarga por job, más lento).
20. justinrainbow/json-schema NO SIRVE para los schemas del MH: son draft-07
    (exclusiveMinimum numérico). Usar opis/json-schema + json_decode() sin
    assoc (exige stdClass; ver convención en ValidadorDte).
21. Toda columna nueva que se escriba por asignación masiva DEBE entrar al
    $fillable de su modelo; Laravel descarta los demás silenciosamente
    (bug del receptor_snapshot: el snapshot nunca se guardó).
22. REGLA DE ORO ante errores de "no se aplicó el cambio": (1) ¿guardé el
    archivo en la ruta exacta? (2) ¿reinicié el worker? (3) optimize:clear.
    El 80% de los "bugs" de esta sesión fueron esos tres.

8. RIESGOS TÉCNICOS YA RESUELTOS (NO REPETIR)
------------------------------------------------------------
- Config cacheada vieja: si algo "no se aplica", php artisan config:clear.
- Limpieza de tenants huérfanos: siempre por SQL directo (evita disparar
  jobs con BD inexistente).
- Namespaces del paquete tenancy: verificar contra vendor/stancl/tenancy;
  la v3.10 es híbrida (managers en TenantDatabaseManagers, contrato en
  Contracts\TenantWithDatabase, trait en Database\Concerns\HasDatabase).
- Cache por tenant: v3 usa tags; drivers file/database no los soportan ->
  CACHE_STORE=array en dev / redis en producción.
- Registro de migraciones vs. tablas reales: si una tabla existe pero su
  migración no está en tenant_xxx.migrations, insertar el registro a mano.
- Migraciones que agregan columnas: usar guardas Schema::hasColumn();
  emisores ya traía nrc/codigo_establecimiento/actividad_economica_desc.
- Windows dev: Memurai como servicio Redis (instalador .msi, puerto 6379);
  verificar con Test-NetConnection 127.0.0.1 -Port 6379.
- hosts: editar como administrador, agregar
  "127.0.0.1 facturadorsv.test demo.facturadorsv.test".
- chillerlan/php-qrcode v5: no existen QRCode::OUTPUT_* (usar string 'png');
  render() devuelve data URI completo: NO base64_encode de nuevo.
- dompdf + QR: pasar el data URI directo al <img>; evitar redimensionar
  por CSS (usar scale del QR para el tamaño final).
- Secuencia de numeroControl: cuenta documentos con numero_control not null
  (los borradores huérfanos no consumen correlativo).
- PHP CLI vs web: verificar extensiones en ambos (gd para el QR).
- Módulo 5: "Ruta [login] no definida" al entrar sin sesión a /admin/*:
  el auth:admin redirige a route('login') por defecto; se define
  redirectGuestsTo en bootstrap/app.php apuntando a admin.login.
- Módulo 5: reescribir routes/tenant.php sin pasar $tenant/$database al
  closure de welcome rompe la vista (500 por variables indefinidas): la
  vista tenant.welcome los usa.
- Módulo 5: "View [admin.planes.index] not found" = la carpeta planes se
  creó DENTRO de tenants (admin\tenants\planes). Debe quedar en
  admin\planes (mismo nivel que tenants y auth).
- Módulo 5: probar vencimiento con vence_en en una suscripcion TRIAL no
  bloquea nada: en trial la fecha que manda es trial_hasta.
- Livewire 4: "el valor aparece en cero / no recalcula" = wire:model simple
  es DIFERIDO en v4; usar wire:model.live(.debounce) para totales en vivo.
- "Table facturador_central.documentos doesn't exist" al escribir en un
  componente Livewire = falta Livewire::setUpdateRoute() con middlewares de
  tenancy (ver Módulo 6).
- Validación local: "Array value found, but an object is required" =
  json_decode con assoc=true pasado al validador; quitar el flag.
- "Use of exclusiveMinimum requires presence of minimum" = librería
  draft-04 contra schema draft-07: cambiar a opis/json-schema.
- opis 4.x: ValidationError ya no tiene dataPointer(); usar
  Opis\JsonSchema\Errors\ErrorFormatter::format($error, true).
- Documento queda en Borrador para siempre = worker de cola detenido
  (Borrador + numero_control = "en cola"). Contingencia = excepción en
  firma/transmisión o worker muerto a mitad del job.
- phpMyAdmin: siempre seleccionar la BD del tenant (tenant_demo) o calificar
  "FROM tenant_demo.documentos"; lo contrario da 1146 o "0 rows".
- El correlativo por count()+1 colisionó (Duplicate entry numero_control):
  huecos por borradores eliminados. Usar max()+1 (ver Módulo 7).

12. CONTEXTO MH (EL SALVADOR) — REFERENCIA RÁPIDA
------------------------------------------------------------
- Ambiente pruebas = 00, producción = 01.
- Base URLs: pruebas https://apitest.dtes.mh.gob.sv,
  producción https://api.dtes.mh.gob.sv (sin barra final en endpoints).
- Endpoints: /seguridad/auth, /fesv/recepciondte, /fesv/recepcionlote,
  /fesv/recepcion/consultadte, /fesv/contingencia, /fesv/anulardte.
- Headers en servicios: Authorization (Bearer token), User-Agent,
  Content-Type application/json.
- Token: 48 h (pruebas) / 24 h (prod); cachear en Redis.
- Firma: JWS compacto del JSON del DTE, hecho por el servicio local
  svfe-api-firmador del MH (POST {firma_url}/firmardocumento/).
- IVA estándar: 13% sobre ventas gravadas (tributo código "20").
- QR público: admin.factura.gob.sv/consultaPublica?ambiente=&codGen=&fechaEmi=
- Documento que se entrega al receptor: JSON con identificacion +
  firmaElectronica + selloRecibido, más representación gráfica (PDF).
